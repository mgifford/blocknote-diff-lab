#2854 — side menu “Add block” and keyboard focus

A verified BlockNote 0.57.0 defect: with the side menu showing, Tab can focus a cloned Add block button from a closing transition, Enter and Space do nothing, and focus falls to document.body. A two-file experimental patch stops the dead focus stop and restores button activation.

Upstream base: 9cb988ff94b60979bbbc62b0ded5cf62fdac88c8 (0.57.0) · Fixture: 4611ae1b (local) · Browser: Chromium 148 / Playwright 1.60 · Recorded 2026-11-23

Verified defect Experimental patch Partial fix

This is a static evidence report, not the live editor comparison. GitHub Pages cannot run BlockNote’s Vite+ dev servers or the local Chromium CDP controller. The live before/after editors and forced-colours emulation run locally with the Diff Lab. The interactive viewer and the source are in the repository.

Problem and affected users

The side menu beside a block contains Add block (+) and Open block menu (six-dot). With the default editor:

  1. Hover a paragraph so the side menu appears and place the caret in that block.
  2. Press Tab.
  3. Focus lands on a cloned, non-interactive copy of Add block. Enter or Space does nothing.
  4. About 250 ms later the copy is removed and focus falls to document.body.

Keyboard-only users lose their place, screen-reader users hear a control that does not work, and switch/voice users cannot activate Add block from the keyboard. The live Add block button also ignores Enter and Space because its click handler is on the icon, not the button.

WCAG 2.2 indicators: 2.1.1 Keyboard, 2.4.3 Focus Order, 2.4.7 Focus Visible, 4.1.2 Name, Role, Value. These are investigation targets, not a conformance finding.

Repeated light runs: Before 3/3 clone → BODY; After 3/3 next control immediately and after 450 ms. The clone has no React props. Pressing Enter or Space on the live Add block opens a suggestion menu only after the patch.

Root cause

The core side-menu extension hides the menu on any keydown while the editor is focused. SideMenuController then removes the live children, and GenericPopover clones the last rendered DOM for the closing transition. That clone is still in the tab order. A separate bug attaches Add block’s onClick to the icon rather than the shared side-menu button.

Experimental patch

Two files in packages/react: mark closing popover snapshots inert, and move Add block activation to the button. The patch applies cleanly to the pinned base. It is not an upstream submission.

Reproduction steps

  1. Open the live comparison locally with the Diff Lab: node bin/diff-lab.mjs start.
  2. Both editors start with the shared two-paragraph fixture. Hover the first paragraph and click it to place the caret.
  3. Press Tab. In Before, focus stays inside the editor after the dead clone disappears; in After, focus reaches Focus after editor.
  4. With the side menu showing, focus Focus after editor, press Shift+Tab twice to reach Add block, then press Enter and Space. The suggestion menu opens only in After.
  5. Repeat at 320px, light, dark, forced-colours light/dark and reduced motion.

Limits

  • This is a partial fix. It prevents focus loss and fixes button activation, but it does not make the side menu discoverable by keyboard alone; that interaction still needs a maintainer decision.
  • Only the default Mantine UI and Chromium 148 were exercised. Ariakit, shadcn, Firefox and Safari are unverified.
  • No human screen-reader session was recorded.
  • The proposed upstream regression test has not been run because BlockNote requires its browser suite to run in Docker.
  • axe-core and Lighthouse are not used to claim a pass for this focus-order defect.
