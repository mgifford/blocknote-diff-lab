# Review protocol

This repository is maintained with a **branch + pull request** workflow. Direct
pushes to `main` are not part of the process.

## Why

`main` deploys the public comparator through GitHub Pages. A direct push
publishes immediately, bypasses review, and makes it hard to separate a test
fix from a content or scope change. The 2026-11-24 accessibility work landed
directly on `main`; that is the exception, recorded in
[`docs/reviews/2026-11-24-direct-main-baseline.md`](reviews/2026-11-24-direct-main-baseline.md),
not the pattern to repeat.

## Branch naming

| Prefix | Use |
| --- | --- |
| `chore/` | Process, CI, dependency or tooling changes |
| `docs/` | Documentation, gap register, ATAG mapping |
| `test/` | Test-only changes or evidence probes |
| `fix/` | A defect fix in the lab or comparator |
| `feat/` | A new lab capability |

Keep one concern per branch. Do not mix a test fix, a docs rewrite, and a
dependency upgrade in one PR.

## Pull request requirements

1. Open a **draft PR** early if the work is exploratory.
2. Fill in the repository PR template with scope, evidence, review focus and the
   checklist.
3. The `page-comparison-tests` check must pass. It runs:
   - `pnpm test` (unit + gap/alignment contracts)
   - `pnpm test:pages`
   - `pnpm test:a11y:local`
4. If the PR touches external previews, run `pnpm test:a11y:previews` and
   `pnpm check:previews` and label the result as upstream context.
5. A reviewer reads the diff, not only the checks. The checks are evidence, not
   approval.
6. Merge only after the review. Prefer **squash merge** so `main` keeps one
   commit per reviewed change.
7. Never merge a PR that the author has not read. If a change was generated by an
   agent, the human owner is the reviewer of record.

## Branch protection

After this protocol is merged, configure a ruleset or branch protection for
`main`:

- require a pull request before merging;
- require the `page-comparison-tests` status check and require branches to be
  up to date;
- block force pushes and deletions;
- include administrators, so the rule applies to the owner too;
- do not require an approval count if there is only one maintainer — that would
  deadlock the repository. Add a required reviewer only when a second reviewer
  exists.

GitHub UI: **Settings → Rules → Rulesets → New branch ruleset**, target
`refs/heads/main`. The job names are stable as `page-comparison-tests`,
`pages-deploy-check`, and `preview-smoke`; the required check for a PR is
`page-comparison-tests`.

Do not enable a required status check that only runs on `main` (such as the
Pages deploy job) as a PR gate; it will never report on the PR.

## Evidence rules

- A passing check is not a review.
- A screenshot is not evidence for a keyboard or screen-reader defect.
- axe and Guidepup Virtual Screen Reader are detectors/simulators, not ATAG
  conformance.
- Upstream PR previews are context only. This repository does not review or
  approve upstream pull requests.
- Real AT and testing with disabled people are out of scope here.
- Raw test output under `reports/` is not committed; cite the command, commit,
  date and result, or a CI run.

## Review checklist

The reviewer should be able to answer:

- What is the user-visible or evidence-visible outcome?
- Which files change, and does the diff match the summary?
- Which tests were run, and what did they prove?
- Which claims are current-main evidence, which are upstream context, and which
  are only proposals?
- Does any wording imply an ATAG conformance level or a PR verdict?
- Are the ATAG/alignment boundaries in
  [`docs/ATAG-ALIGNMENT-ISSUES.md`](ATAG-ALIGNMENT-ISSUES.md) preserved?
- Is a generated report, screenshot, or local path accidentally committed?
